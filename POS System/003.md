## Transaction & Database Concept — ACID, Rollback (နက်နက်ရှိုင်းရှိုင်း)

### Transaction ဆိုတာ database အဆင့်မှာ ဘာလဲ

Database မှာ **Transaction** ဆိုတာ SQL statement တွေအစုအဝေးတစ်ခုကို **"တစ်ခုတည်းသော logical unit"** အနေနဲ့ run တာပါ။ Cafe POS ရဲ့ "Order ပေးချေ" event ကို SQL အနေနဲ့ ခွဲကြည့်ရအောင်:

```sql
-- Order တစ်ခု payment ယူတယ်ဆိုပါစို့ (Coffee 2 ခွက်, Cake 1 ခု)
INSERT INTO orders (cashier_id, total, status, created_at) VALUES (...);
INSERT INTO order_items (order_id, product_id, qty, price) VALUES (...);
INSERT INTO order_items (order_id, product_id, qty, price) VALUES (...);
UPDATE products SET stock = stock - 2 WHERE id = 1;  -- coffee stock လျှော့
UPDATE products SET stock = stock - 1 WHERE id = 5;  -- cake stock လျှော့
INSERT INTO payments (order_id, amount, method) VALUES (...);
```

SQL statement **6 ခု** ရှိပါတယ်။ Statement 3 ခုမြောက်မှာ error တက်ရင် (ဥပမာ database connection ပြတ်တယ်) — statement 1, 2 က run ပြီးသားဆိုတော့ order က database ထဲ ဝင်ပြီးသားဖြစ်နေပေမယ့် stock လျှော့ခြင်း၊ payment record က မဝင်တော့ဘူး။

**ဒါက data ပျက်တာပါ** — order ရှိနေတယ်၊ ဒါပေမယ့် payment record မရှိဘူး၊ stock လည်း ကောင်းကောင်းမလျှော့ဘူး။ Report ထုတ်ရင် sales count နဲ့ inventory count မကိုက်တော့ဘူး။

ဒါကို ကာကွယ်ဖို့ statement 6 ခုလုံးကို **transaction block** ထဲ ထည့်လိုက်တယ်:

```sql
START TRANSACTION;
INSERT INTO orders ...;
INSERT INTO order_items ...;
INSERT INTO order_items ...;
UPDATE products SET stock = stock - 2 WHERE id = 1;
UPDATE products SET stock = stock - 1 WHERE id = 5;
INSERT INTO payments ...;
COMMIT;  -- အားလုံးအောင်မြင်မှ ဒီတစ်ခါတည်း database ထဲ permanent ဖြစ်တယ်
```

Statement ၆ ခုထဲက တစ်ခုမှားရင် `COMMIT` အစား `ROLLBACK` ခေါ်လိုက်ရင် — database ဟာ `START TRANSACTION` မခေါ်ခင် အခြေအနေကို **ပြန်ပြောင်းတယ်** (INSERT/UPDATE တွေအားလုံး ပယ်ဖျက်)။ "ဘာမှမဖြစ်သလို" ပြန်ဖြစ်သွားတယ်။

### ACID — အက္ခရာလေးလုံးရဲ့ အဓိပ္ပာယ်

**A — Atomicity (တစ်စုတည်း)** Transaction ထဲက statement အားလုံး "အားလုံးအောင်မြင် (all)" ဒါမှမဟုတ် "ဘာမှမဖြစ် (nothing)" ပဲ ဖြစ်ရမယ်။ "ဝက်ဝက်ခြမ်း" ဆိုတာ မရှိရဘူး။

> POS ဥပမာ: Payment success ဖြစ်ပြီး stock deduct fail ဖြစ်တာမျိုး မဖြစ်စေရဘူး။

**C — Consistency (ညီညွတ်မှု)** Transaction မစခင်နဲ့ ပြီးတဲ့နောက် database ရဲ့ rule (constraint) တွေအားလုံး မှန်နေရမယ်။ ဥပမာ stock ဟာ negative မဖြစ်ရဘူးဆိုတဲ့ rule ရှိရင်, transaction ပြီးတဲ့အခါ ဒီ rule ကို ချိုးဖောက်လို့ မရဘူး။

> POS ဥပမာ: Coffee stock 1 ခွက်ပဲ ကျန်တော့တယ်၊ Customer က 2 ခွက် order လုပ်ရင် — transaction က stock = -1 ဖြစ်အောင် လုပ်ခွင့်မပြုသင့်ဘူး (application logic က ဒါကို check ပြီးမှ transaction စရမယ်)။

**I — Isolation (သီးခြားစီ run နေတာ)** Cashier 2 ယောက်က တစ်ချိန်တည်း POS 2 လုံးကနေ coffee last stock 1 ခွက်ကို တစ်ပြိုင်နက် order ယူမယ်ဆိုပါစို့။ Isolation က ကာကွယ်ပေးတာက — transaction တစ်ခုက run နေတုန်း, အခြား transaction တစ်ခုက ဝင်ရောစွက်ဖက်လို့မရအောင်။

> ဒါမပါရင် ဖြစ်နိုင်တဲ့ bug: Cashier A နဲ့ B နှစ်ယောက်စလုံးက "stock = 1, OK order လက်ခံမယ်" ဆိုပြီး တစ်ပြိုင်နက် decide လုပ်ကြရင် — coffee 2 ခွက် ရောင်းပြီးသားဖြစ်နေပေမယ့် stock မှာ 1 ခွက်ပဲ ရှိတာဆိုတော့ **overselling** ဖြစ်သွားမယ်။ Isolation (Row locking) က ဒါကို ကာကွယ်ပေးတယ်။

**D — Durability (တည်တံ့မှု)** `COMMIT` လုပ်ပြီးရင် (power ပျက်တာ၊ server crash ဖြစ်တာ ဘာဖြစ်ဖြစ်) data ဟာ database ထဲမှာ ထာဝရ ကျန်နေရမယ်။

> POS ဥပမာ: Payment commit ပြီးတဲ့ 1 စက္ကန့်အကြာမှာ server crash ဖြစ်ရင်တောင် — server ပြန် on လာတဲ့အခါ ဒီ order record ရှိနေရမယ်။

### Java JDBC နဲ့ Transaction ရေးနည်း (POS ရဲ့ Payment Service အတွက်)

Default အားဖြင့် JDBC ရဲ့ `Connection` ဟာ **auto-commit mode** မှာရှိပါတယ် — statement တစ်ကြောင်းစီ run တာနဲ့ database ထဲ ချက်ချင်း commit ဖြစ်သွားတယ် (rollback လုပ်ခွင့် မရှိဘူး)။ Transaction control ကို manual လုပ်ချင်ရင် auto-commit ကို ပိတ်ရမယ်:

```java
public class OrderService {

    public boolean checkoutOrder(Order order, List<OrderItem> items, Payment payment) {
        Connection conn = null;
        try {
            conn = DatabaseConnection.getConnection();
            conn.setAutoCommit(false);  // ← transaction control စတယ်

            // 1. orders table ထဲ insert
            int orderId = orderDao.insert(conn, order);

            // 2. order_items insert
            for (OrderItem item : items) {
                item.setOrderId(orderId);
                orderItemDao.insert(conn, item);

                // 3. stock deduct
                boolean success = productDao.deductStock(conn, item.getProductId(), item.getQty());
                if (!success) {
                    // stock မလုံလောက်ရင် (race condition ဖြစ်ခဲ့ရင်)
                    throw new InsufficientStockException(item.getProductId());
                }
            }

            // 4. payment record insert
            payment.setOrderId(orderId);
            paymentDao.insert(conn, payment);

            conn.commit();  // ← အားလုံးအောင်မြင်မှ permanent ဖြစ်
            return true;

        } catch (Exception e) {
            if (conn != null) {
                try {
                    conn.rollback();  // ← တစ်ခုခု fail ရင် အားလုံးပြန်ဖျက်
                } catch (SQLException ex) {
                    logger.error("Rollback failed", ex);
                }
            }
            logger.error("Checkout failed", e);
            return false;

        } finally {
            if (conn != null) {
                try {
                    conn.setAutoCommit(true);  // ← connection pool ကို ပြန်ပေးခင် ပုံမှန် state ပြန်ထားရမယ်
                    conn.close();
                } catch (SQLException ex) {
                    logger.error("Connection cleanup failed", ex);
                }
            }
        }
    }
}
```

**သတိထားရမယ့် အဓိက point တွေ:**

1. `conn.setAutoCommit(false)` — transaction ကို manual control ယူတယ်
2. DAO method တွေ (`insert`, `deductStock`) ကို **connection object တစ်ခုတည်း** pass ချရမယ် — DAO တစ်ခုစီက connection အသစ်စီ ယူရင် transaction တစ်ခုတည်းအောက် မရှိတော့ဘူး
3. Exception ဖြစ်ရင် `catch` ထဲမှာ `rollback()` မဖြစ်မနေ ခေါ်ရမယ်
4. `finally` ထဲမှာ connection ကို auto-commit ပြန်ထားပြီးမှ close/return (connection pool ကို ပြန်ပို့ခင်)

### Isolation ကို Code ထဲ ဘယ်လို ကိုင်တွယ်လဲ (Overselling ကာကွယ်ခြင်း)

`deductStock` method ထဲမှာ ဒီလို **atomic check-and-update** SQL တစ်ကြောင်းတည်းနဲ့ ရေးရမယ် — Java code ထဲမှာ "stock ကြည့်→ if enough → update" ဆိုပြီး 2 ဆင့်ခွဲရေးရင် race condition ဖြစ်နိုင်ပါတယ်:

```java
public boolean deductStock(Connection conn, int productId, int qty) throws SQLException {
    String sql = "UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?";
    PreparedStatement ps = conn.prepareStatement(sql);
    ps.setInt(1, qty);
    ps.setInt(2, productId);
    ps.setInt(3, qty);  // ← stock >= qty ဖြစ်မှသာ update ဖြစ်မယ်
    int rowsAffected = ps.executeUpdate();
    return rowsAffected > 0;  // 0 ဆိုရင် stock မလုံလောက်လို့ update မဖြစ်ဘူး
}
```

ဒီလို `WHERE stock >= ?` condition ထည့်ထားခြင်းအားဖြင့် — MySQL ရဲ့ row-level lock က ဒီ row ကို update လုပ်နေတုန်း အခြား transaction က ဒီ row ကို တစ်ပြိုင်နက် update လုပ်ခွင့်မရှိတော့ဘူး (InnoDB engine default behavior)။ ဒါက Cashier 2 ယောက် တစ်ပြိုင်နက် coffee last 1 ခွက်ကို order ယူတဲ့ scenario ကို ပြေလည်အောင် ကိုင်တွယ်ပေးတယ် — တစ်ယောက်ပဲ အောင်မြင်ပြီး၊ အခြားတစ်ယောက်ကတော့ `rowsAffected = 0` ဖြစ်ပြီး `InsufficientStockException` throw ဖြစ်မယ်။

---

ဒါက **ACID + Rollback + Isolation/Locking** ရဲ့ core concept နဲ့ code implementation ပါ။

နောက်ဆက်ချင်တဲ့ topic ရွေးပါ:

1. **try-with-resources** နဲ့ transaction ကို ပိုသေချာအောင် ရေးနည်း (resource leak ကာကွယ်ခြင်း)
2. **Connection Pool (HikariCP)** — connection တစ်ခုချင်း create/close မလုပ်ဘဲ pool ကနေ ဘယ်လို reuse လုပ်လဲ
3. Layered Architecture concept ကို ဆက်နက်ရှိုင်းအောင် လေ့လာမယ်
