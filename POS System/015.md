# DTO (Data Transfer Object) - လိုအပ်ရဲ့လား

## ၁။ DTO ဆိုတာ ဘာလဲ (အရင်ဆုံး ရှင်းရအောင်)

DTO ဆိုတာ **layer တစ်ခုကနေ တစ်ခုကို data ပို့တဲ့အခါ သုံးတဲ့ container class** ပါ။ Model (Entity) class နဲ့ တူတူပုံစံပါပဲ - field တွေပဲ ပါတယ်၊ logic မပါဘူး။

**Entity/Model vs DTO ရဲ့ ကွာခြားချက်:**

- **Entity** (`Product.java`) → database table structure နဲ့ တိုက်ရိုက် တူတယ် (`product_id`, `category_id`, `price`, `stock_qty`...)
- **DTO** (`ProductDisplayDTO.java`) → View layer အတွက်ပဲ လိုအပ်တဲ့ field တွေ ပြန်ဖော်ထားတာ (ဥပမာ - `category_id` အစား `categoryName` ကို string အနေနဲ့ join လုပ်ပြီးသား ပြန်ပေးတာ)

## ၂။ ဘာလို့ DTO လိုအပ်တတ်လဲ (Theory)

**Problem**: Entity class ကို layer အားလုံးမှာ တိုက်ရိုက် သုံးလိုက်ရင် -

- Database structure ပြောင်းတိုင်း (column ထည့်/ဖျက်) View layer code ပါ ထိသွားနိုင်တယ် (tight coupling)
- Entity ထဲမှာ password hash လိုမျိုး sensitive field ပါနေရင် View layer ဆီ လိုအပ်တာထက် ပိုပို့မိတတ်တယ်
- View layer အတွက် join လုပ်ထားတဲ့ data (ဥပမာ - category name, ရိုးရိုး `category_id` မဟုတ်ဘဲ) ကို ဘယ်လို ပို့မလဲ ဆိုတဲ့ ပြဿနာ

**DTO ရဲ့ ဖြေရှင်းချက်**: Layer တစ်ခုချင်းစီအတွက် သီးသန့် "view" data shape ကို ခွဲထုတ်တာပါ။

## ၃။ မင်းရဲ့ Cafe POS Project အတွက် - **လိုအပ်ဘူး**

ရှေ့က "must know vs skip" logic အတိုင်းပဲ ဆုံးဖြတ်ကြရအောင်:

### DTO မလိုအပ်တဲ့ အကြောင်းအရင်း

1. **Scale သေးတယ်**: Cafe POS က large enterprise system (microservices, REST API, mobile+web client အများကြီး) မဟုတ်ဘူး - Swing desktop app တစ်ခုတည်းပါ။ Client အများကြီးအတွက် data shape ကွဲပြားစွာ ပို့ဖို့ မလိုအပ်ဘူး။
    
2. **Entity ကိုတိုက်ရိုက်သုံးလည်း ပြသနာမရှိဘူး**: `Product` object ကို DAO → Service → View အထိ တိုက်ရိုက် pass လုပ်လို့ရတယ်။ Swing app တစ်ခုတည်းထဲမှာ (network boundary မရှိ) DTO ရဲ့ အဓိက အကျိုးကျေးဇူး (serialization boundary, API contract) ကို အသုံးမပြုဖြစ်ဘူး။
    
3. **Extra complexity**: DTO ထည့်ရင် - Entity → DTO ပြောင်း (mapping) code ထပ်ရေးရမယ်၊ class အရေအတွက် နှစ်ဆတိုးမယ်၊ project အသေးအတွက် **over-engineering** ဖြစ်သွားနိုင်တယ်။
    

### DTO Concept ကို "တစိတ်တပိုင်း" သုံးသင့်တဲ့ နေရာ

Full DTO pattern မလိုပေမယ့်၊ **join/aggregate ဖြစ်တဲ့ data** အတွက်တော့ သေးငယ်တဲ့ helper class လိုအပ်တတ်ပါတယ်:

> ဥပမာ - `JTable` ထဲမှာ Order History ပြချင်ရင် - order data + customer name + employee name ပေါင်းပြီး row တစ်ခုအဖြစ် ပြချင်တယ်။ ဒါက `Order` entity တစ်ခုတည်းနဲ့ မလုံလောက်ဘူး (customer name က `customers` table ထဲမှာ)။ ဒါမျိုးအတွက် `OrderSummaryView` (သို့) `OrderTableRow` ဆိုတဲ့ သေးငယ်တဲ့ class လိုအပ်တတ်တယ် - ဒါကို "DTO" လို့ ခေါ်လည်းရ၊ "ViewModel" လို့ ခေါ်လည်းရပါတယ်။ Pattern အနေနဲ့ formal DTO layer တစ်ခုလုံး တည်ဆောက်ရန် မလိုပဲ **လိုအပ်တဲ့နေရာမှာပဲ** ဒီလို helper class ထည့်ရုံပါ။

## ၄။ အနှစ်ချုပ် ဆုံးဖြတ်ချက်

|Approach|Project size|ဒီ project အတွက်|
|---|---|---|
|Entity ကို layer အားလုံးမှာ တိုက်ရိုက်သုံး|Small-medium desktop app|✅ **သုံးပါ**|
|Full DTO pattern (layer တိုင်းအတွက် DTO ရေး)|Enterprise, multi-client, REST API|❌ လိုအပ်ချင်မှ လိုအပ်မယ်|
|Join/display အတွက်ပဲ helper class|ဘယ် project အရွယ်အစားမဆို|✅ လိုအပ်ရင် သုံးပါ (ဥပမာ - table view)|

**ရိုးရှင်းတဲ့ Rule of Thumb**: "DTO လိုမလို" ဆိုတာကို project စလက်ကတည်းက စဉ်းစားနေစရာမလိုဘူး - Entity ကို တိုက်ရိုက်စသုံးပါ။ နောက်မှ "screen တစ်ခုမှာ table ပြဖို့ data ပုံစံ ရှုပ်နေတယ်" ဆိုတဲ့ ပြဿနာ တကယ်တွေ့မှ helper/view-model class ထပ်ထည့်ပါ - YAGNI (You Aren't Gonna Need It) principle အတိုင်းပါ။
