ရှင်းပါတယ်။ Feature list ချရေးတာမဟုတ်ဘဲ **"ဘာကြောင့် ဒီလိုဒီဇိုင်းလုပ်ရလဲ"** ဆိုတဲ့ core concept ကို focus လုပ်ပြီး ရှင်းပြပါ့မယ်။

## Core Concept 1: POS System ရဲ့ "နှလုံးသား" — Transaction ဆိုတာဘာလဲ

POS system တစ်ခုလုံးရဲ့ အဓိက concept က **"Transaction"** တစ်ခုတည်းပါပဲ။ ကျန်တာအားလုံးက transaction ကို support လုပ်ဖို့ ဖွဲ့စည်းထားတာချည်းပါ။

**Transaction ဆိုတာ**: Customer တစ်ယောက် item တွေ ဝယ်ပြီး ပိုက်ဆံပေးချေတဲ့ event တစ်ခုလုံးကို ခေါ်တာပါ။ ဒီ event ထဲမှာ အဆင့်တွေရှိတယ်:

```
စတင် (Order created, status = OPEN)
  → item ထည့်/ဖျက် (Cart state ပြောင်း)
  → payment ယူ (status = PAID)
  → stock လျှော့ (Inventory update)
  → receipt ထုတ် (Record permanent)
```

**ဘာကြောင့် ဒီ concept က အရေးကြီးလဲ?**

Transaction တစ်ခုဟာ **"all-or-nothing"** ဖြစ်ရမယ်ဆိုတဲ့ principle ရှိပါတယ် — ဒါကို **Atomicity** လို့ခေါ်ပါတယ် (database ACID property ထဲက A)။ ဥပမာ:

- Customer က coffee 2 ခွက် order လုပ်, payment ပေးတယ်
- Payment success ဖြစ်ပေမယ့် stock deduct မှာ error တက်ရင် → coffee stock က မှားနေတော့မယ်
- ဒါကြောင့် payment + stock deduction + order record ကို **တစ်ခုတည်း transaction** အနေနဲ့ database မှာ COMMIT လုပ်ရမယ်၊ တစ်ခုမအောင်မြင်ရင် အားလုံး ROLLBACK ဖြစ်ရမယ်

ဒါကို code level မှာ Java JDBC transaction (`conn.setAutoCommit(false)`, `conn.commit()`, `conn.rollback()`) နဲ့ implement လုပ်ရမှာပါ — ဒါကို Part 11 (Payment) မှာ code နဲ့ ပြပေးမှာပါ။

## Core Concept 2: Layered Architecture — "ဘာကြောင့် Layer ခွဲရလဲ"

Swing project ကြီးတွေမှာ code အားလုံးကို button click event ထဲမှာ တိုက်ရိုက်ရေးလို့မရပါဘူး။ ဒါကြောင့် layer ခွဲတယ်:

```
UI Layer (JFrame/JPanel)       → user ဘာမြင်လဲ၊ ဘာ click လုပ်လဲ
      ↓ calls
Service Layer (Business Logic)  → "total ဘယ်လိုတွက်မလဲ", "discount apply လုပ်လို့ရလား"
      ↓ calls
DAO Layer (Data Access)         → database ကနေ data ယူ/ထည့်
      ↓ uses
Model Layer (POJO/Entity)       → Product, Order, User စတဲ့ data structure
```

**ဘာကြောင့် ဒီလို ခွဲရလဲ?** — core concept က **"Separation of Concerns"** ပါ။

- UI layer က "ဘယ်လို ပြမလဲ" ကိုပဲ သိသင့်တယ်၊ "total ဘယ်လိုတွက်မလဲ" ဆိုတာကို မသိသင့်ဘူး
- ဥပမာ Discount rule ပြောင်းချင်ရင် (10% ကနေ 15% ပြောင်းမယ်ဆိုရင်), Service layer ထဲက code line တစ်ကြောင်းပဲ ပြောင်းရမယ်၊ UI code ကို မထိရဘူး
- Test လုပ်ရအလွယ်ဆုံး — Service layer ကို UI မပါဘဲ logic တစ်ခုတည်း test လုပ်လို့ရတယ်

ဒါကြောင့် Cafe POS မှာ **"Add to cart button ကို click လုပ်ရင် ဘာဖြစ်လဲ"** ဆိုတာကို trace လုပ်ကြည့်ရအောင်:

```
1. UI: "Add" button click → ProductPanel.onAddClick()
2. UI က CartService.addItem(product, qty) ကို ခေါ်
3. Service: business rule check (stock ရှိလား? qty valid လား?)
4. Service: Cart object ထဲ item ထည့်, subtotal recalculate
5. UI: Cart table ကို refresh လုပ်ပြီး UI ပြန်ပြ
```

DAO/Database က ဒီအဆင့်မှာ **မပါသေးဘူး** — Cart ဆိုတာ order confirm မလုပ်မချင်း memory ထဲမှာပဲ ရှိနေသေးတဲ့ object ပါ (database ထဲ မရေးသေးဘူး)။ ဒါက concept တစ်ခုပါ — **"Cart is transient, Order is persistent"**။

## Core Concept 3: Session — "ဘယ်သူ login ဝင်နေလဲ ဘယ်လိုသိမလဲ"

Swing က desktop app ဖြစ်လို့ web app လို HTTP session cookie မလိုပါဘူး။ ဒါပေမယ့် concept တူတူပါပဲ:

**Session ဆိုတာ**: Application တစ်ခုလုံးမှာ "ဘယ်သူ login ဝင်နေလဲ" ဆိုတဲ့ state ကို global တစ်နေရာမှာ သိမ်းထားတာပါ။

Java Swing single-JVM app မှာ ဒါကို **Singleton pattern** နဲ့ implement လေ့ရှိပါတယ်:

```java
public class SessionManager {
    private static SessionManager instance;
    private User currentUser;
    private LocalDateTime loginTime;
    
    private SessionManager() {}
    
    public static SessionManager getInstance() {
        if (instance == null) instance = new SessionManager();
        return instance;
    }
    // login, logout, getCurrentUser...
}
```

**ဘာကြောင့် Singleton လိုလဲ?** — Application တစ်ခုလုံးထဲက panel/screen တိုင်းက "ဘယ်သူ login ဝင်နေလဲ" ဆိုတာကို object တစ်ခုတည်းကနေ query လုပ်ချင်လို့ပါ (ဥပမာ receipt ထုတ်တဲ့အခါ cashier name ထည့်ဖို့)။

ဒါက Role-based access control ရဲ့ base concept လည်း ဖြစ်ပါတယ် — `SessionManager.getInstance().getCurrentUser().getRole()` ကို check ပြီးမှ Admin menu ပြမလား ဆုံးဖြတ်တာပါ။

ဆက်ပြီး ဘယ် concept ကို နက်နက်ရှိုင်းရှိုင်း ဆက်လေ့လာချင်လဲ — Transaction/Database concept (ACID, rollback), Layered Architecture (interface design), ဒါမှမဟုတ် Session/State management လား?
