# GraphQL API အသေးစိတ်

## GraphQL ဆိုတာဘာလဲ

**GraphQL** ဆိုတာ Facebook က 2012 ခုနှစ်လောက်မှာ internal သုံးဖို့ တီထွင်ခဲ့ပြီး 2015 မှာ open-source လုပ်ခဲ့တဲ့ **query language** တစ်ခုဖြစ်ပါတယ်။ REST/SOAP လို protocol မဟုတ်ဘဲ **API အတွက် data ကို ဘယ်လို query/manipulate လုပ်မလဲ ဆိုတဲ့ specification** ဖြစ်ပါတယ်။

## REST ရဲ့ ပြဿနာ — GraphQL ဖြေရှင်းချက်

### Over-fetching (လိုချင်တာထက် ပိုရခြင်း)

REST API မှာ `GET /users/123` ခေါ်ရင် server က user object ရဲ့ field **အားလုံး** ပြန်ပေးပါတယ် — user name ကိုပဲ လိုချင်ပေမယ့် address, phone, orders history အားလုံးပါလာမယ်။

### Under-fetching (မလုံလောက်ခြင်း)

User ရဲ့ orders history ကိုပါ လိုချင်ရင် `GET /users/123` ခေါ်ပြီးမှ `GET /users/123/orders` ကို **request ထပ်ပို့ရ**ပါမယ် — multiple round-trip လိုအပ်ပါတယ်။

**GraphQL** က ဒီပြဿနာနှစ်ခုလုံးကို client ဘက်က **ကိုယ်လိုချင်တဲ့ field ကိုပဲ တိတိကျကျ ရွေးပြီး request တစ်ခါတည်းနဲ့ ရယူ**နိုင်အောင် ဖြေရှင်းပေးပါတယ်။

## Query ဥပမာ

**Request:**

```graphql
query {
  user(id: 123) {
    name
    email
    orders {
      id
      total
    }
  }
}
```

**Response:**

```json
{
  "data": {
    "user": {
      "name": "Aung Aung",
      "email": "aungaung@example.com",
      "orders": [
        { "id": 1, "total": 50000 },
        { "id": 2, "total": 25000 }
      ]
    }
  }
}
```

Client က `name`, `email`, `orders.id`, `orders.total` field တွေကိုပဲ ရွေးထားလို့ — server ဘက်က ဒီ field တွေကိုပဲ ပြန်ပေးပါတယ်၊ တခြား field (address, phone) တွေ ပါမလာပါ။ **Request တစ်ခါတည်းနဲ့** user data + orders data ကို တစ်ပြိုင်နက် ရလိုက်ပါတယ်။

## GraphQL ရဲ့ Operation အမျိုးအစား ၃ မျိုး

### ၁။ Query (Read data)

```graphql
query {
  user(id: 123) {
    name
  }
}
```

### ၂။ Mutation (Create/Update/Delete data)

```graphql
mutation {
  createUser(name: "Su Su", email: "susu@example.com") {
    id
    name
  }
}
```

### ၃။ Subscription (Real-time — WebSocket ပေါ်မှာ အခြေခံ)

```graphql
subscription {
  orderStatusChanged(orderId: 456) {
    status
    updatedAt
  }
}
```

> **Subscription** က WebSocket ရဲ့ concept ကို GraphQL layer ပေါ်မှာ တင်ထားတာပါ — real-time update လိုအပ်ရင် သုံးပါတယ်။

## Single Endpoint

REST မှာ resource တစ်ခုစီအတွက် endpoint ခွဲထားရပေမယ့် (`/users`, `/orders`, `/products`) GraphQL မှာတော့ **endpoint တစ်ခုတည်း** (ပုံမှန် `/graphql`) ကနေ query type အလိုက် request structure ထဲမှာ ဖော်ပြပါတယ်:

```
POST /graphql
```

## Schema (Type System)

GraphQL API တိုင်းမှာ **Schema** ဆိုတာ ရှိပါတယ် — SOAP ရဲ့ WSDL လိုမျိုးပါပဲ၊ ဒါပေမယ့် ပိုရိုးရှင်းပါတယ်:

```graphql
type User {
  id: ID!
  name: String!
  email: String!
  orders: [Order]
}

type Order {
  id: ID!
  total: Float!
}

type Query {
  user(id: ID!): User
}

type Mutation {
  createUser(name: String!, email: String!): User
}
```

`!` mark က "required field" ကို ဆိုလိုပါတယ်။

## REST vs SOAP vs GraphQL — နှိုင်းယှဉ်ချက်

||REST|SOAP|GraphQL|
|---|---|---|---|
|Endpoint|Multiple (resource-based)|Multiple/Single (operation-based)|Single|
|Data format|JSON/XML|XML ချည်းသာ|JSON|
|Over/Under-fetching|ဖြစ်တတ်|ဖြစ်တတ်|မဖြစ် (client ရွေးလို့ရ)|
|Contract|Optional|WSDL (required)|Schema (required)|
|Learning curve|ရိုးရှင်း|ရှုပ်ထွေး|အလယ်အလတ်|
|Caching|Easy (HTTP cache)|ခက်|ခက် (query ကွဲပြားလို့)|
|Real-time|မရ (WebSocket ခွဲသုံးရ)|မရ|Subscription built-in|

## Java မှာ GraphQL Client ခေါ်ခြင်း

GraphQL ရဲ့ transport layer က **HTTP POST** ကို အခြေခံထားတာမို့ REST API ခေါ်တဲ့ HttpClient pattern အတိုင်းပဲ သုံးလို့ရပါတယ်၊ ကွာတာက **query string ကို JSON body ထဲမှာ ထည့်ပို့ရ**တာပါ:

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.http.HttpRequest.BodyPublishers;

public class GraphQLClient {

    public static String fetchUser(int userId) throws Exception {
        String query = """
            {
              "query": "query { user(id: %d) { name email orders { id total } } }"
            }
            """.formatted(userId);

        HttpClient client = HttpClient.newHttpClient();
        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create("https://api.example.com/graphql"))
                .header("Content-Type", "application/json")
                .POST(BodyPublishers.ofString(query))
                .build();

        HttpResponse<String> response = client.send(request,
                HttpResponse.BodyHandlers.ofString());

        return response.body(); // JSON response — Jackson နဲ့ parse လုပ်ရပါမယ်
    }
}
```

### Variables သုံးတဲ့ Query (Recommended Approach)

String concatenation (`%d`) အစား **variables** သုံးတာ safer ပါတယ် (SQL injection ကာကွယ်သလိုမျိုး):

```java
String requestBody = """
    {
      "query": "query GetUser($id: ID!) { user(id: $id) { name email } }",
      "variables": { "id": "%d" }
    }
    """.formatted(userId);
```

### Dedicated GraphQL Library — DGS Client / graphql-java-client

Manual HttpClient အစား library သုံးချင်ရင် **Netflix DGS** framework ရဲ့ client, ဒါမှမဟုတ် **Apollo Kotlin/Java client** တို့ကို သုံးလို့ရပါတယ် — type-safe query builder ပါဝင်လို့ ပိုအဆင်ပြေပါတယ်။

## Swing App မှာ SwingWorker ထဲ ချိတ်ဆက်ခြင်း

Pattern အတူတူပါပဲ — `doInBackground()` မှာ GraphQL query ပို့၊ `done()` မှာ UI update:

```java
public class GraphQLUserWorker extends SwingWorker<String, Void> {
    private final int userId;

    public GraphQLUserWorker(int userId) {
        this.userId = userId;
    }

    @Override
    protected String doInBackground() throws Exception {
        return GraphQLClient.fetchUser(userId);
    }

    @Override
    protected void done() {
        try {
            String jsonResult = get();
            // Jackson JsonNode နဲ့ parse ပြီး JTable/JLabel update
        } catch (Exception e) {
            // error handling
        }
    }
}
```

## GraphQL Response ရဲ့ Error Handling

GraphQL ရဲ့ special point တစ်ခုက — error ဖြစ်ရင်တောင် HTTP status code က **200 OK** ပြန်လာနိုင်ပါတယ် (REST လို 404/500 မဟုတ်ဘဲ)။ Error detail က response body ထဲက `errors` field မှာ ပါလာပါတယ်:

```json
{
  "data": null,
  "errors": [
    { "message": "User not found", "path": ["user"] }
  ]
}
```

ဒါကြောင့် response ကို parse လုပ်တဲ့အခါ HTTP status code ကိုပဲ မကြည့်ဘဲ **`errors` field ရှိမရှိ** ကိုပါ စစ်ရပါမယ်။

## ဘယ်အခါ GraphQL ကို ရွေးသင့်လဲ

|Scenario|GraphQL သင့်တော်ပါသလား|
|---|---|
|Mobile app (data usage/battery limited)|✅ Over-fetching ရှောင်လို့ရလို့|
|Complex nested data (multiple related resources)|✅ Single request နဲ့ ရနိုင်လို့|
|Simple CRUD API (small project)|❌ REST က ပိုရိုးရှင်း|
|Public API caching လိုအပ်|❌ REST က HTTP cache ပိုအဆင်ပြေ|
|Real-time + flexible query နှစ်ခုလုံးလိုချင်|✅ Subscription + flexible query ပါလို့|
