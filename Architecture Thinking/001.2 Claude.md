QRCode project အတွက် ဒီ registration flow ကို system design အနေနဲ့ စဉ်းစားကြည့်ရအောင်—သင့် project structure (`com.ams.qrcode`, Student model, qr_path မသိမ်းတော့ဘူးလို့ ဆုံးဖြတ်ထားတာ) နဲ့ ကိုက်ညီအောင် ဆွေးနွေးပေးမယ်။

## 1. Entity တွေ

- **Student** — admin က register လုပ်တဲ့အခါ ဖန်တီးမယ့် entity (studentId, name, class, admissionDate, `accountStatus` = PENDING/ACTIVE)
- **Account** — student ကိုယ်တိုင် register ပြီးမှ ဖြစ်ပေါ်လာမယ့် entity (username, passwordHash, studentId FK, createdAt)
- **Admin** — student register လုပ်တဲ့ user
- **RegistrationToken** — QR ထဲမှာ ထည့်မယ့် secure token (token string, studentId FK, expiryTime, isUsed flag) — ဒါကို သီးခြား entity အနေနဲ့ ထားသင့်တယ်၊ QR ကို "studentId ချည်း" မထည့်သင့်ဘူး (အောက်မှာ ရှင်းပြမယ်)

## 2. Module တွေ

- **Admin Module** — student register, QR/ID card generate
- **QR Generation Module** — token ဖန်တီးပြီး QR image encode
- **Registration Module** — QR scan → token validate → account create
- **Auth Module** — login, session/token issue
- **DAO/DB Module** — သင့်ရဲ့ existing structure

## 3. Relationship

```
Admin  1 ────< N  Student
Student 1 ──── 1  Account       (registration ပြီးမှ ဖြစ်)
Student 1 ──── 1  RegistrationToken   (pending အချိန်ထိပဲ ရှိ၊ used ဖြစ်ရင် invalidate)
```

## 4. Flow

1. Admin က Student ကို register → `Student` row ဖန်တီး၊ `accountStatus = PENDING`
2. System က **RegistrationToken** တစ်ခု auto-generate (studentId + random secret, expiry 24-48hr)
3. QR image ကို token ကနေ encode → ID card ပေါ်မှာ print (သင် ဆုံးဖြတ်ထားသလိုပဲ QR path ကို DB မှာ မသိမ်းဘူး၊ studentId convention နဲ့ file name လုပ်ထားတာလည်း ဆက်သုံးနိုင်တယ်)
4. Student က QR scan → App/Web က token ကို server ကို ပို့
5. Server က token validate (expiry check, used check, signature check)
6. Valid ဆိုရင် — Student ကို registration form (username/password ရွေးချယ်ခွင့်) ပြ
7. Submit လုပ်ရင် → `Account` row create, `RegistrationToken.isUsed = true`, `Student.accountStatus = ACTIVE`

## 5. QR ရဲ့ တာဝန်

QR က **identification + integrity proof** ပဲ လုပ်သင့်တယ်:

- ဘယ် student အတွက်ဆိုတာ point လုပ်ပေးတယ်
- Server ကို hit လုပ်ဖို့ token ကို ဆောင်သွားတယ်
- QR ထဲမှာ password/sensitive data မထည့်ရဘူး — token တစ်ခုတည်း (random, unguessable) ပဲ ပါသင့်တယ်

⚠️ **အရေးကြီးတာ**: QR ထဲမှာ studentId ကို plain text အနေနဲ့ ချည်းထည့်ရင် တစ်ယောက်က IDs တွေကို guess/enumerate လုပ်ပြီး တခြားသူ့ account ကို register လုပ်ပစ်နိုင်တယ်။ ဒါကြောင့် **random token (UUID/HMAC-signed)** ကို သုံးဖို့ လိုတယ်။

## 6. Account ရဲ့ တာဝန်

- Login credential သိမ်းတာ (password ကို bcrypt/argon2 နဲ့ hash လုပ်ပြီး)
- Authentication လုပ်ပေးတာ (login အချိန်)
- Session/JWT token ထုတ်ပေးတာ (login ပြီးရင် app ကို ဆက်သုံးဖို့)
- Student ရဲ့ data ကို access ခွင့်ပြုတာ (authorization)

## 7. Security ဘယ်နေရာမှာလိုမလဲ

|နေရာ|ဘာလုပ်ရမလဲ|
|---|---|
|Token generation|Random, cryptographically secure (UUID v4 / signed HMAC)|
|Token expiry|24-48 hr, ကုန်ရင် admin က ပြန် regenerate|
|Token usage|Single-use — account created ပြီးရင် invalidate|
|Registration endpoint|Rate limiting (brute-force token guessing ကာကွယ်)|
|Password|Hash (bcrypt/argon2), plain text မသိမ်းရ|
|Transport|HTTPS/TLS (RMI သုံးရင် သင် RMI security part မှာ လုပ်ခဲ့တဲ့ SSL/auth ကို ဆက်သုံးနိုင်)|
|Duplicate check|Student.accountStatus == ACTIVE ဆိုရင် register ထပ်မလုပ်ပေးရ|

## 8. Error ဖြစ်ရင်

- **Token မရှိ/invalid** → "QR code မမှန်ကန်ပါ၊ Admin ကို ဆက်သွယ်ပါ" ပြ
- **Token expired** → "QR code သက်တမ်းကုန်ပါပြီ၊ Admin ဆီက ID card အသစ် တောင်းပါ"
- **Token already used** → "ဒီ account ရှိပြီးသားပါ၊ Login လုပ်ပါ" (login page ကို redirect)
- **Student not found** → generic error (attacker ကို ဘယ် studentId မှန်တယ်ဆိုတာ မသိစေရဘူး)
- **Network/Server error** → retry option ပြပေးပြီး friendly message
