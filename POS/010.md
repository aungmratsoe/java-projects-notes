# Database Design (ER Diagram) — Concept Level, Normalization, FK Design Decisions

## ၁. Normalization — ဘာကြောင့် လိုအပ်လဲ

Normalization ဆိုတာ data redundancy (ထပ်နေတဲ့ data) ကို လျှော့ချပြီး **data integrity** ကို ထိန်းသိမ်းဖို့ table structure ကို organize လုပ်တာပါ။ Cafe POS မှာ normalize မလုပ်ရင် ဖြစ်တတ်တဲ့ ပြဿနာ:

**Bad design (unnormalized) — sales table တစ်ခုတည်းထဲမှာ အားလုံးထည့်ထားရင်**:

```
sale_id | cashier_name | item_name | item_price | qty
1       | Aye Aye      | Latte     | 3500       | 2
2       | Aye Aye      | Latte     | 3500       | 1
```

ဒီလို design မှာ ပြဿနာတွေ:

- **Update anomaly**: Latte ဈေးပြောင်းရင် row တိုင်းကို update လုပ်ရမယ်
- **Insertion anomaly**: menu item အသစ်တစ်ခု sale မဖြစ်သေးရင် system ထဲ ထည့်လို့မရ
- **Deletion anomaly**: sale record တစ်ခုတည်းကို ဖျက်ရင် item info ပါ ပျောက်သွားနိုင်တယ်

## ၂. Normal Forms — Concept Level

- **1NF (First Normal Form)**: column တစ်ခုစီမှာ value တစ်ခုတည်း ရှိရမယ် (atomic) — "Latte, Cappuccino" လို comma-separated list တစ် cell ထဲ မထည့်ရ
- **2NF**: composite primary key ရှိတဲ့ table မှာ, column တိုင်းက key တစ်ခုလုံးပေါ် depend ဖြစ်ရမယ် (partial dependency မရှိရ)
- **3NF**: non-key column တစ်ခုက non-key column တခြားတစ်ခုပေါ် depend မဖြစ်ရ (transitive dependency မရှိရ) — ဥပမာ `item_price` ကို `sales` table ထဲ မထားဘဲ `menu_items` ထဲပဲ ထားရမယ်

Practical rule: **"each fact stored once"** — Cafe POS အတွက် 3NF အထိ normalize လုပ်ရင် လုံလောက်ပါတယ်။

## ၄. Foreign Key Design Decisions — ဘာကြောင့် ဒီလို ချိတ်ထားလဲ

**`sales.shift_id` နှင့် `sales.cashier_id` — နှစ်ခုစလုံး ထားသင့်လား**

ဒီနေရာမှာ design decision တစ်ခု ရှိတယ် — `cashier_id` ကို `sales` table ထဲ ထပ်ထည့်ဖို့ (redundant) လိုသလား၊ `shift_id` ကနေ `shifts.cashier_id` ကို join လုပ်ရင်ရမလား ဆိုတာ။

- **Join-only approach (3NF strict)**: `sales.shift_id` ပဲ ထား၊ cashier ကို သိချင်ရင် `shifts` table ကို join
- **Denormalize slightly**: `sales.cashier_id` ကိုပါ ထပ်ထည့် (redundant ဖြစ်ပေမယ့် performance အတွက်)

Cafe POS မှာ sales report query (cashier-wise sales) က frequent operation ဖြစ်တာမို့, `cashier_id` ကို `sales` ထဲ ထားတာက **practical denormalization** ဖြစ်တယ် — theory အရ 3NF ကို strict လိုက်စားရင် `shifts` join ချည်းသုံးရမယ်၊ ဒါပေမယ့် real-world POS system တွေမှာ query performance အတွက် ဒီလို trade-off လုပ်လေ့ရှိတယ်။

**`sale_items.unit_price` — ဘာကြောင့် `menu_items.price` ကို join မလုပ်ဘဲ ထပ်ကူးထားလဲ**

ဒါက **အရေးအကြီးဆုံး FK design decision** ပါ — `sale_items` ထဲမှာ `menu_item_id` (FK) ရှိပြီးသားဆိုတော့ `unit_price` ကို ဘာကြောင့် ထပ်သိမ်းရသလဲလို့ မေးစရာရှိတယ်။ အဖြေက **historical accuracy**:

- Latte ဈေး ဒီနေ့ ¥3,500 ဆိုပါစို့၊ လာမည့်လ ¥4,000 ဖြစ်သွားရင်
- Sale record ဟောင်းတွေကို `menu_items.price` ကနေ join ဆွဲရင်, ဈေးဟောင်းနဲ့ ရောင်းခဲ့တဲ့ sale record ရဲ့ total က **ဒီနေ့ ဈေးအသစ်** နဲ့ ပြောင်းသွားမယ် — ဒါက **incorrect audit trail**

ဒါကြောင့် `sale_items.unit_price` ကို "at the time of sale" snapshot အနေနဲ့ ထပ်ကူးသိမ်းထားရမယ် — ဒါက denormalization ပေမယ့် **intentional** ဖြစ်တယ်။ ဒီလိုမျိုး "ဒီ fact က time-sensitive snapshot ဖြစ်လို့ ရည်ရွယ်ချက်ရှိရှိ ထပ်ကူးထားတယ်" ဆိုတာကို design document ထဲ comment ထားသင့်တယ်။

**`categories` ကို ဘာကြောင့် ခွဲထုတ်ရသလဲ**

`menu_items.category_name` ကို string အဖြစ် တိုက်ရိုက်ထားလို့ရပေမယ့်, category အသစ်ထည့်/rename လုပ်ရင် row အားလုံးကို update လုပ်ရမယ် (update anomaly)။ `categories` table ခွဲထားပြီး `menu_items.category_id` FK ချိတ်ထားရင် category rename တစ်ခါတည်း လုပ်လို့ရတယ် — classic 3NF benefit ပါ။

## ၅. Cardinality သတိထားရမယ့်အချက်

- `users` → `shifts`: **1-to-many** (cashier တစ်ယောက်က shift အများကြီးဖွင့်နိုင်၊ shift တစ်ခုက cashier တစ်ယောက်တည်းရဲ့)
- `sales` → `sale_items`: **1-to-many** (sale တစ်ခုမှာ item အများကြီး ပါနိုင်) — ဒီ split ကတော့ classic **order/order-line pattern** ပါ၊ `sales` table ထဲမှာ item list ကို ထည့်လို့မရလို့ (1NF violation ဖြစ်မယ်) ဒါကြောင့် `sale_items` ဆိုတဲ့ junction-like table ခွဲထားရတာ

---

`shifts` table ရဲ့ `status` column ကို enum/constraint ဘယ်လို enforce ရမလဲ၊ ဒါမှမဟုတ် index design (query performance အတွက် ဘယ် column တွေကို index လုပ်သင့်လဲ) ကို ဆက်လေ့လာချင်လား?
