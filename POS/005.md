## Layered Architecture — နက်နက်ရှိုင်းရှိုင်း

### ဘာကြောင့် "Layer" ဆိုတဲ့ concept လိုအပ်လဲ — Layer မခွဲရင် ဘာဖြစ်လဲ

Layer မခွဲဘဲ Swing button event ထဲမှာ တိုက်ရိုက်ရေးရင် ဒီလို code ဖြစ်လာတတ်ပါတယ်:

```java
addToCartButton.addActionListener(e -> {
    // UI code ထဲမှာ database query, business rule အားလုံး ရောနေတယ်
    Connection conn = DriverManager.getConnection(URL, USER, PASS);
    PreparedStatement ps = conn.prepareStatement("SELECT * FROM products WHERE id = ?");
    ps.setInt(1, selectedProductId);
    ResultSet rs = ps.executeQuery();
    
    if (rs.next()) {
        int stock = rs.getInt("stock");
        double price = rs.getDouble("price");
        
        if (stock <= 0) {
            JOptionPane.showMessageDialog(this, "Out of stock!");
            return;
        }
        
        double subtotal = price * quantitySpinner.getValue();
        cartTableModel.addRow(new Object[]{productName, quantity, subtotal});
        
        // total ပြန်တွက်
        double total = 0;
        for (int i = 0; i < cartTableModel.getRowCount(); i++) {
            total += (double) cartTableModel.getValueAt(i, 2);
        }
        totalLabel.setText(String.valueOf(total));
    }
    conn.close();
});
```

ဒီလို code ရဲ့ ပြဿနာက **"concern" (ကိစ္စအမျိုးအစား) 3-4 မျိုးက line တစ်ကြောင်းတည်းမှာ ရောနေတာ**ပါ:

- UI concern (button, dialog ပြခြင်း)
- Business rule concern (stock ရှိလား, total ဘယ်လိုတွက်လဲ)
- Data access concern (SQL query, connection)

**ဒါက ဘာကြောင့် ဆိုးလဲ?**

1. **Reusability မရှိဘူး** — Admin dashboard မှာလည်း "stock ရှိလား" ဆိုတဲ့ rule ကို ပြန်သုံးချင်ရင်, ဒီ SQL+logic တစ်ခုလုံးကို button တိုင်းမှာ copy-paste ရမယ်။ Rule ပြောင်းချင်ရင် (ဥပမာ "stock <= 5 ဆိုရင် warning ပြမယ်" လို့ ပြောင်းချင်ရင်) button 5-6 နေရာကို ရှာပြီး ပြင်ရမယ်။
    
2. **Test မလုပ်နိုင်ဘူး** — "stock ရှိရင် cart ထဲ ထည့်, မရှိရင် reject" ဆိုတဲ့ business rule ကို Swing UI မပါဘဲ (button click မလိုဘဲ) test လုပ်ချင်ရင် — code က UI ထဲ ရောနေလို့ မလုပ်နိုင်တော့ဘူး။
    
3. **Database ပြောင်းလို့ ခက်တယ်** — နောက်တစ်နေ့ MySQL ကနေ PostgreSQL ပြောင်းရမယ်ဆိုရင်, SQL code က UI code တွေထဲ ကွဲနေတော့ ရှာပြင်ရခက်တယ်။

### Layer 4 ခု — တစ်ခုချင်းစီရဲ့ "တာဝန်" (Responsibility) သတ်သတ်မှတ်မှတ်

```
┌─────────────────────────────────────┐
│   UI Layer (JFrame, JPanel)          │  "ဘယ်လိုပြမလဲ"
├─────────────────────────────────────┤
│   Service Layer (Business Logic)     │  "ဘာလုပ်သင့်လဲ"
├─────────────────────────────────────┤
│   DAO Layer (Data Access Object)     │  "database ကို ဘယ်လို ရေး/ဖတ်မလဲ"
├─────────────────────────────────────┤
│   Model Layer (POJO)                 │  "data က ဘယ်လို shape လဲ"
└─────────────────────────────────────┘
```

**Rule တစ်ခု အရေးကြီးတယ်**: Layer တစ်ခုက **အောက်ခြေ layer ကိုပဲ** ခေါ်ခွင့်ရှိတယ် — အပေါ်ကို ပြန်ခေါ်လို့ မရဘူး။ UI → Service → DAO → Database (ဒီလမ်းကြောင်းတစ်ခုတည်းပဲ)။ DAO က Service ကို ပြန်ခေါ်လို့ မရဘူး, Service က UI ကို တိုက်ရိုက် import လုပ်လို့ မရဘူး။

### Model Layer — "Data ရဲ့ ပုံစံ"

```java
public class Product {
    private int id;
    private String name;
    private double price;
    private int stock;
    private int categoryId;
    
    // constructor, getters, setters
}
```

Model က **logic မပါဘဲ data ကိုပဲ** ကိုယ်စားပြုတယ် — database row တစ်ကြောင်းကို Java object အနေနဲ့ ပြောင်းထားတာပါ။

### DAO Layer — "Database နဲ့ တိုက်ရိုက်ပြောသူ"

```java
public class ProductDAO {
    
    public Product findById(int id) throws SQLException {
        String sql = "SELECT * FROM products WHERE id = ?";
        try (Connection conn = DatabaseConnection.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setInt(1, id);
            try (ResultSet rs = ps.executeQuery()) {
                if (rs.next()) {
                    Product p = new Product();
                    p.setId(rs.getInt("id"));
                    p.setName(rs.getString("name"));
                    p.setPrice(rs.getDouble("price"));
                    p.setStock(rs.getInt("stock"));
                    return p;
                }
            }
        }
        return null;
    }
    
    public boolean deductStock(Connection conn, int productId, int qty) throws SQLException {
        String sql = "UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?";
        try (PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setInt(1, qty);
            ps.setInt(2, productId);
            ps.setInt(3, qty);
            return ps.executeUpdate() > 0;
        }
    }
}
```

**DAO ရဲ့ rule**: SQL code ကို DAO ထဲမှာပဲ ရေးရမယ် — Service layer, UI layer ဘယ်နေရာမှာမှ SQL string မပါစေရဘူး။ DAO က "stock ရှိလား" ဆိုတဲ့ business decision မချသင့်ဘူး — data ကို ယူ/ပြင်ပေးရုံပဲ လုပ်တယ် (`deductStock` က WHERE condition ကို SQL level constraint အနေနဲ့ ထားတာ — ဒါက data integrity အတွက်, business rule ဆုံးဖြတ်ချက်မဟုတ်ဘူး)။

### Service Layer — "Business Rule ရဲ့ နေရာ"

```java
public class CartService {
    private ProductDAO productDAO = new ProductDAO();
    private List<CartItem> cartItems = new ArrayList<>();
    
    public void addItem(int productId, int qty) throws InsufficientStockException, SQLException {
        Product product = productDAO.findById(productId);
        
        // Business rule: stock လုံလောက်လား စစ်တယ်
        if (product.getStock() < qty) {
            throw new InsufficientStockException(product.getName());
        }
        
        CartItem item = new CartItem(product, qty);
        cartItems.add(item);
    }
    
    public double calculateTotal() {
        return cartItems.stream()
                .mapToDouble(item -> item.getProduct().getPrice() * item.getQty())
                .sum();
    }
    
    public double calculateTotalWithDiscount(double discountPercent) {
        double total = calculateTotal();
        return total - (total * discountPercent / 100);
    }
}
```

"Stock ရှိလား", "total ဘယ်လိုတွက်လဲ", "discount ဘယ်လိုတွက်လဲ" — ဒါတွေအားလုံးက **business rule** ဖြစ်လို့ Service layer ထဲမှာပဲ ရှိရမယ်။ ဒါက concept အရေးကြီးတဲ့အချက်ပါ — **"Business logic က UI framework ကနေ လုံးဝ လွတ်လပ်ရမယ်"**။ ဆိုလိုတာက `CartService` class ထဲမှာ `import javax.swing.*` တစ်ခွန်းမှ မပါသင့်ဘူး။

**ဘာကြောင့် ဒါက အရေးကြီးလဲ?** — နောက်ဖြစ်နိုင်ချေ ဥပမာ: Cafe POS ကို web app လို့ ပြောင်းချင်လာမယ်ဆိုပါစို့ (Swing အစား web UI)။ Service layer + DAO layer ကို **တစ်ကြောင်းမှမပြောင်းဘဲ** ပြန်သုံးနိုင်ရမယ် — UI layer ချည်းပဲ အသစ် ရေးရမှာပါ။

### UI Layer — "ပြသခြင်း + user input လက်ခံခြင်း"

```java
public class POSPanel extends JPanel {
    private CartService cartService = new CartService();
    
    private void onAddToCartClick() {
        int productId = getSelectedProductId();
        int qty = (int) quantitySpinner.getValue();
        
        try {
            cartService.addItem(productId, qty);
            refreshCartTable();
            totalLabel.setText(formatCurrency(cartService.calculateTotal()));
        } catch (InsufficientStockException ex) {
            JOptionPane.showMessageDialog(this, "Stock မလုံလောက်ပါ: " + ex.getMessage());
        } catch (SQLException ex) {
            JOptionPane.showMessageDialog(this, "Database error ဖြစ်ပါတယ်");
            logger.error("DB error", ex);
        }
    }
}
```

UI layer မှာ ဖြစ်နေတာက — `cartService.addItem()` ကို **ခေါ်ရုံပဲ**၊ SQL query ဘယ်လိုရေးလဲ, stock check logic ဘယ်လိုလဲ ဆိုတာ UI က လုံးဝမသိပါဘူး။ Exception ရလာရင် dialog ပြရုံပဲ တာဝန်ရှိတယ်။

### Cafe POS မှာ "Add to Cart" flow ကို layer အလိုက် trace လုပ်ကြည့်ရအောင် (အနှစ်ချုပ်)

```
[UI]      button click
    ↓ cartService.addItem(productId, qty) ခေါ်
[Service] productDAO.findById(productId) ခေါ် (data ယူ)
    ↓
[DAO]     SQL SELECT run, Product object return
    ↓ (Service ဆီ ပြန်)
[Service] business rule check → stock < qty ဆို exception throw
    ↓ (UI ဆီ ပြန်)
[UI]      exception ဖမ်း → dialog ပြ / success ဆို table refresh
```

Layer တစ်ခုစီက **တာဝန်တစ်ခုတည်းပဲ** ယူထားတာ သတိထားပါ — ဒါကို software engineering မှာ **Single Responsibility Principle** လို့ခေါ်ပါတယ်။

ဆက်ချင်တာ ရွေးပါ:

1. **Exception design** — `InsufficientStockException` လို custom exception တွေကို layer ကြားမှာ ဘယ်လို design လုပ်သင့်လဲ (checked vs unchecked)
2. **DTO vs Model** — Service ကနေ UI ဆီ data ပြန်ပို့တဲ့အခါ Model (Entity) ကိုတိုက်ရိုက်ပို့သင့်လား DTO သီးသန့်ရှိသင့်လား
3. Session/State management concept ကို ဆက်လေ့လာမယ်
