# Access Control ရဲ့ Logic Concept - နက်နက်ရှိုင်းရှိုင်း သင်ယူကြမယ်

ကောင်းပါပြီ၊ code မထည့်ဘဲ **logic/concept** ကိုပဲ တစ်ဆင့်ချင်း ရှင်းပြပေးပါမယ်။ ဒါက Computer Security သင်ခန်းစာထဲက classic topic တစ်ခုပါ။

## ၁။ ပြဿနာက ဘာလဲ

Multi-user system တစ်ခုမှာ user အားလုံးက resource အားလုံးကို လွတ်လပ်စွာ access လုပ်ခွင့်ရှိရင် အန္တရာယ်ရှိပါတယ်။ Cashier တစ်ယောက်က menu ဈေးနှုန်း ပြောင်းနိုင်ရင်၊ ဒါမှမဟုတ် ဝန်ထမ်း salary ကြည့်နိုင်ရင် ဆိုးပါတယ်။

ဒါကြောင့် **"ဘယ်သူက ဘာလုပ်ခွင့်ရှိလဲ"** ဆိုတာကို စနစ်တကျ ဆုံးဖြတ်ဖို့ model တစ်ခု လိုအပ်ပါတယ်။

## ၂။ အခြေခံ Concept သုံးခု

Access control ရဲ့ **အခြေခံ entity သုံးမျိုး** ရှိပါတယ်:

1. **Subject** (ပြုလုပ်သူ) - user, role, employee
2. **Object** (ပြုလုပ်ခံရသူ/ရာ) - resource, data, table, function
3. **Operation** (ဘာလုပ်ခွင့်လဲ) - Create, Read, Update, Delete (CRUD)

**Access Matrix ရဲ့ core logic** ကတော့ ဒီသုံးခုကို triple (Subject, Object, Operation) အနေနဲ့ ချိတ်ဆက်ထားတာပါ။

> "Subject S သည် Object O အပေါ် Operation P ကို ပြုလုပ်ခွင့် ရှိသလား?" → **True/False**

Matrix ရဲ့ cell တစ်ခုချင်းစီက ဒီမေးခွန်းရဲ့ အဖြေကို သိမ်းထားတာပါ။

## ၃။ ဘာလို့ "Matrix" လို့ခေါ်လဲ

```
              Products    Orders    Employees
Cashier         R          CRU         -
Manager        CRUD        CRUD        R
Admin          CRUD        CRUD       CRUD
```

Row = Subject, Column = Object, Cell = Permission set - ဒါက mathematical matrix ပုံစံနဲ့ တူလို့ "Access Control Matrix" လို့ခေါ်တာပါ (Lampson's Access Matrix Model, 1971 ကနေ စတင်ခဲ့တာ)။

**Logic အရ** ဒီ matrix ကို row အလိုက်ခွဲကြည့်ရင် **Capability List** (ဒီ subject က ဘာတွေလုပ်ခွင့်ရှိလဲ) ဖြစ်ပြီး၊ column အလိုက်ခွဲကြည့်ရင် **Access Control List (ACL)** (ဒီ object ကို ဘယ်သူတွေ access လုပ်ခွင့်ရှိလဲ) ဖြစ်သွားပါတယ်။ Database structure ချင်း တူပေမယ့် "ဘယ်ဘက်က ကြည့်လဲ" ဆိုတာချင်း ကွာတာပါ။

## ၄။ ဘာလို့ Direct Matrix (User↔Permission) မသုံးဘဲ Role ကို အလယ်ထည့်လဲ

ဒါက key logic ပါ။ Naive approach က user တစ်ယောက်ချင်းစီအတွက် permission သီးသန့်ပေးတာပါ:

```
User123 → can DELETE products
User456 → can DELETE products
```

Employee ၅၀ ဆိုရင် permission assignment ၅၀ ကြိမ် သီးခြားစီ management လုပ်ရမယ် - ဒါက **scalability problem** ပါ (N users အတွက် N × M permissions)။

**RBAC (Role-Based Access Control)** ရဲ့ logic ကတော့ **indirection layer** တစ်ခု ထပ်ထည့်တာပါ:

```
User → Role → Permission
```

Employee 50 ယောက်ရှိပေမယ့် Role ကတော့ Admin/Manager/Cashier/Barista လေးမျိုးပဲ ရှိပါတယ်။ Permission ကို Role အဆင့်မှာသာ define လုပ်ပြီး၊ user တစ်ယောက်ချင်းစီကို role တစ်ခု assign လုပ်လိုက်ရုံပါပဲ။

**ဒါက logic အရ ဘာကို ဖြေရှင်းလဲ:**

- **Scalability**: Employee အသစ်ဝင်ရင် role ချထားရုံပဲ (permission အသစ် ပြန်ရေးစရာမလို)
- **Consistency**: Manager အားလုံးက permission တစ်မျိုးတည်းရှိမယ်၊ လူတစ်ယောက်ချင်းအလိုက် ကွဲမသွားဘူး
- **Auditability**: "Cashier တွေ ဘာတွေလုပ်ခွင့်ရှိလဲ" ဆိုတာ တစ်နေရာတည်းမှာ ကြည့်လို့ရ

## ၅။ Permission Checking ရဲ့ Logic Flow

Runtime မှာ access decision ဆုံးဖြတ်တဲ့ logic ကတော့ ဒီအတိုင်းပါ:

```
1. User login → System က user ရဲ့ role ကို ရှာတွေ့
2. Role ကနေ permission set ကို ဆွဲထုတ်
3. User က action တစ်ခု လုပ်ချင်တဲ့အခါ:
   → (role, object, operation) ကို permission set ထဲမှာ ရှိ/မရှိ စစ်
   → ရှိရင် → Allow
   → မရှိရင် → Deny
```

ဒီ logic ကို **"Default Deny"** principle နဲ့ တည်ဆောက်ရပါတယ် - ဆိုလိုတာက matrix ထဲမှာ **明示的**(explicit) ခွင့်ပြုမထားရင် default အနေနဲ့ **ပိတ်ပင်**ထားရမယ် (allow-list model)။ Blacklist model (default allow, ပိတ်ချင်တာပဲ ရေးထား) ကတော့ security အရ အန္တရာယ်ပိုများပါတယ် - ဘာလို့လဲဆိုတော့ permission အသစ် module ထပ်တိုးလာတိုင်း "ဒါကို ဘယ်သူတွေ ပိတ်ရမလဲ" ဆိုတာ မေ့သွားနိုင်လို့ပါ။

## ၆။ Least Privilege Principle

Access matrix ဒီဇိုင်းရေးဆွဲရာမှာ လိုက်နာရမယ့် အရေးကြီးဆုံး principle တစ်ခုက **"Principle of Least Privilege"** ပါ:

> Subject တစ်ယောက်ကို သူ့လုပ်ငန်းတာဝန် ပြီးမြောက်ဖို့ **လိုအပ်တဲ့ permission အနည်းဆုံး**ပဲ ပေးရမယ်။

ဒါကြောင့် Cashier ကို "Employees" table အတွက် permission လုံးဝ မပေးထားတာပါ (သူ့အလုပ်နဲ့ မသက်ဆိုင်လို့)။ ဒါက "convenience" (အားလုံးကို access ပေးလိုက်ရင် code ရေးရလွယ်) ထက် "security" ကို ဦးစားပေးတဲ့ decision ပါ။

## ၇။ Static vs Dynamic Permission

နောက်ထပ် သင်ထားသင့်တဲ့ concept တစ်ခုက - permission check ကို **ဘယ်အဆင့်မှာ** လုပ်သင့်လဲ ဆိုတာပါ:

- **Static/Coarse-grained**: "ဒီ role က ဒီ module ကို access လုပ်ခွင့်ရှိသလား" (module level)
- **Dynamic/Fine-grained**: "ဒီ cashier က _သူ့ shift_ အတွင်း ဖန်တီးထားတဲ့ order ကိုပဲ cancel လုပ်ခွင့်ရှိသလား၊ တခြားလူရဲ့ order ကိုတော့ မရှိဘူး" (row-level/instance level)

POS system တစ်ခုမှာ "Cashier က order cancel လုပ်ခွင့်ရှိသေးတယ်၊ ဒါပေမယ့် Manager approval လိုတယ်" ဆိုတာမျိုးဆို ဒါက **fine-grained** logic ဖြစ်ပြီး၊ simple matrix တစ်ခုတည်းနဲ့ ဖော်ပြလို့ မလုံလောက်တော့ဘဲ business rule (code logic) ကို ထပ်ဖြည့်ရပါတယ်။

---

ဒီ concept တွေထဲက ဘယ်အပိုင်းကို ပိုနက်နက်ရှိုင်းရှိုင်း လေ့လာချင်ပါသလဲ - Least Privilege vs Separation of Duties လိုမျိုး security principle တွေလား၊ ဒါမှမဟုတ် RBAC ရဲ့ Role Hierarchy (Manager ကို Cashier permission အားလုံး အလိုအလျောက်ရအောင် inherit လုပ်နည်း) ကိုလား?
