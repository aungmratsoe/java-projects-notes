## DTO vs Model (Entity) — Service ကနေ UI ဆီ ဘာပို့သင့်လဲ

### အရင်ဆုံး Model/Entity ဆိုတာ ဘယ်လိုအခန်းကဏ္ဍမှာ ရှိလဲ ပြန်သတိရအောင်

Model (Entity) ဆိုတာ **database table တစ်ခုကို တိုက်ရိုက် ကိုယ်စားပြု** တဲ့ class ပါ:

```java
public class Product {
    private int id;
    private String name;
    private double price;
    private int stock;
    private int categoryId;
    private String supplierCode;   // internal use, cost tracking
    private double costPrice;      // ဆိုင်ဝယ်ဈေး (profit margin တွက်ဖို့)
    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;
    // getters/setters
}
```

ဒီ class ထဲမှာ `costPrice` (ဆိုင်ကဝယ်တဲ့ဈေး) ဆိုတဲ့ field ပါနေတယ် သတိပြုပါ — ဒါက **admin/owner ပဲ သိသင့်တဲ့ data** ဖြစ်နိုင်ပါတယ် (profit margin ကို cashier မမြင်စေချင်ဘူးဆိုပါစို့)။

### Model ကို UI ဆီ တိုက်ရိုက်ပို့ရင် ဘာပြဿနာဖြစ်လဲ

Cashier ရဲ့ POS screen ဘက်က `ProductDAO.findAll()` ကို ခေါ်ပြီး `Product` object list ကို UI ဆီ **တိုက်ရိုက်ပို့**ရင်:

```java
List<Product> products = productDAO.findAll();  // costPrice ပါတဲ့ object အပြည့်
productTable.setModel(products);  // UI layer ဆီ ရောက်သွားပြီ
```

Cashier ဘက်က UI ကို **decompile/inspect** လုပ်ခြင်းအားဖြင့် (Java app ဖြစ်တာကြောင့် byte code ကနေ ပြန်ရအောင် ဖတ်လို့ရတယ်) `costPrice` field ပါလာတဲ့ object ရဲ့ data ကို ရရှိနိုင်ပါတယ် — **security/business risk** တစ်ခုပါ။

ဒါ့အပြင် ပိုအရေးကြီးတဲ့ concept ကတော့ — **"Coupling" (တွဲနေခြင်း)** ပြဿနာပါ။ UI layer က `Product` entity ရဲ့ field structure အတိအကျကို "သိ" နေရတယ်။ Database schema ပြောင်းရင် (ဥပမာ `costPrice` column အသစ်ထည့်မယ်, `supplierCode` ဖျက်မယ်) — Entity class ပြောင်းရင် UI code တွေပါ ချက်ချင်း break ဖြစ်နိုင်ပါတယ်။ Database layer နဲ့ UI layer က **တစ်ခုတည်း structure ကို မျှဝေသုံးနေလို့** ဒီလိုဖြစ်တာပါ။

### DTO (Data Transfer Object) — ဘယ်လို concept လဲ

DTO ဆိုတာ **layer တစ်ခုကနေ တစ်ခုဆီ "ဘာ data လိုအပ်လဲ" ဆိုတာကိုပဲ** ကိုယ်စားပြုတဲ့ သီးသန့် class ပါ — database structure နဲ့ လုံးဝ မဆိုင်ပါဘူး, purpose-built ပါ။

Cafe POS ရဲ့ POS screen (cashier ကြည့်မယ့်) အတွက် DTO ဥပမာ:

```java
public class ProductDisplayDTO {
    private int id;
    private String name;
    private double sellingPrice;   // costPrice မပါဘူး — cashier မမြင်ရ
    private int stock;
    private String categoryName;   // categoryId မဟုတ်ဘဲ name တိုက်ရိုက် (UI မှာ display လွယ်အောင်)
    private String imagePath;
    // getters/setters — logic မပါဘူး
}
```

Service layer ကနေ ဒီလို DTO ကို build ပြီးမှ UI ဆီ ပို့တယ်:

```java
public class ProductService {
    private ProductDAO productDAO = new ProductDAO();
    private CategoryDAO categoryDAO = new CategoryDAO();
    
    public List<ProductDisplayDTO> getProductsForPOSScreen() throws SQLException {
        List<Product> products = productDAO.findAll();  // full entity, internal use
        List<ProductDisplayDTO> result = new ArrayList<>();
        
        for (Product p : products) {
            ProductDisplayDTO dto = new ProductDisplayDTO();
            dto.setId(p.getId());
            dto.setName(p.getName());
            dto.setSellingPrice(p.getPrice());     // costPrice မထည့်ဘူး
            dto.setStock(p.getStock());
            
            Category cat = categoryDAO.findById(p.getCategoryId());
            dto.setCategoryName(cat.getName());    // 2 table ကနေ ပေါင်းစပ်ထား
            
            result.add(dto);
        }
        return result;
    }
}
```

သတိပြုစရာ — DTO ထဲမှာ `categoryName` ဆိုတဲ့ field က `Product` table ထဲမှာ လုံးဝမရှိပါဘူး (`Category` table ကနေ join/lookup ယူထားတာ)။ ဒါက DTO ရဲ့ core concept ပါ — **"UI ဘာမြင်ချင်လဲ" ကို base ပြုပြီး design လုပ်တာ**, "database ဘယ်လိုသိမ်းလဲ" ကို base မလုပ်ဘူး။

### ဘယ်အချိန်မှာ DTO လိုအပ်လဲ, ဘယ်အချိန်မှာ Model ကို တိုက်ရိုက်သုံးလို့ရလဲ

Cafe POS project size (student/personal project, table အနည်းငယ်) အတွက် **အမြဲတမ်း DTO ခွဲစရာ မလိုပါဘူး** — ဒါက practical trade-off တစ်ခုပါ:

**Model ကို တိုက်ရိုက်သုံးလို့ရတဲ့ scenario:**

- Internal admin screen (Admin ကိုယ်တိုင် product edit လုပ်တဲ့ form) — Admin ဆိုရင် `costPrice` မြင်လည်း ပြဿနာမရှိဘူး
- Field အားလုံးကို UI မှာ ဒီအတိုင်း ပြသင့်တဲ့ simple CRUD screen

**DTO လိုအပ်တဲ့ scenario (Cafe POS မှာ concrete ဥပမာတွေ):**

1. **Sensitive field ဖုံးထားချင်ရင်** — POS screen (cashier) မှာ `costPrice` မပြချင်ဘူး
2. **Table ၂ ခုကို ပေါင်းပြချင်ရင်** — Receipt DTO တစ်ခုမှာ Order + Customer name + Cashier name + Product list ကို table 4 ခုကနေ ပေါင်းပြချင်ရင်
3. **Report/Aggregate data** — "Best-selling product" report က `SUM(qty)`, `product_name` ပဲ လိုအပ်တာ, `Product` entity တစ်ခုလုံး မလိုဘူး

```java
// Report အတွက် DTO ဥပမာ — database column ဘယ်တစ်ခုနဲ့မှ တိုက်ရိုက်မကိုက်ဘူး
public class BestSellerReportDTO {
    private String productName;
    private int totalSold;
    private double totalRevenue;
}
```

```java
// Receipt အတွက် DTO ဥပမာ — table 3-4 ခုကနေ ပေါင်းစပ်ထား
public class ReceiptDTO {
    private String orderNumber;
    private String cashierName;
    private LocalDateTime orderTime;
    private List<ReceiptLineItemDTO> items;
    private double subtotal;
    private double tax;
    private double discount;
    private double total;
    private double cashReceived;
    private double change;
}
```

`ReceiptDTO` က `Order` table, `User` table (cashier name), `OrderItem` table တွေ ပေါင်းစပ်ထားတာမို့ — database table structure နဲ့ **တစ်ခုနဲ့မှ တိုက်ရိုက်ကိုက်ညီမှု မရှိပါဘူး**။ ဒါဟာ DTO ရဲ့ အဓိကရည်ရွယ်ချက်ကို ပြသနေပါတယ် — **"UI/output ဘာလိုချင်လဲ" ဆိုတဲ့ shape ကို ကိုယ်စားပြုတာ**, database schema ကို ကိုယ်စားပြုတာ မဟုတ်ပါဘူး။

### Core Concept အနှစ်ချုပ် — Model vs DTO ရဲ့ "အနှစ်သာရ ကွာခြားချက်"

||**Model (Entity)**|**DTO**|
|---|---|---|
|ကိုယ်စားပြုတာ|Database table တစ်ခု|UI/output က လိုချင်တဲ့ shape|
|ဘယ်နေရာသုံး|DAO ↔ Service layer ကြားမှာ|Service ↔ UI layer ကြားမှာ|
|Field|Table column အားလုံး ပါတတ်တယ်|လိုသလောက်ပဲ, table အများကြီးက ပေါင်းလို့ရ|
|ပြောင်းလဲမှု|Database schema အလိုက် ပြောင်း|Screen/report requirement အလိုက် ပြောင်း|

ဒီ concept ရဲ့ အနှစ်ချုပ်ကတော့ — **Layer 2 ခု (Database layer, Presentation layer) က "အမြဲတမ်း reason တစ်ခုတည်းအတွက်ပဲ ပြောင်းသင့်တယ်"** ဆိုတဲ့ software design principle ပါ (Single Responsibility ရဲ့ extension version)။ Database structure ပြောင်းလို့ UI break မဖြစ်စေချင်ရင်, UI requirement ပြောင်းလို့ database schema ကို မထိချင်ရင် — DTO က ဒီနှစ်ခုကြားမှာ "buffer/boundary" အဖြစ် ရပ်ပေးတာပါ။

---

ဆက်ချင်တာ ရွေးပါ:

1. **Exception design** — checked vs unchecked exception ကို layer တစ်ခုချင်းစီမှာ ဘယ်လို ကိုင်တွယ်သင့်လဲ
2. **Session/State management** concept ကို ဆက်နက်ရှိုင်းအောင် (login session, current user, shift tracking)
3. Database Design (ER Diagram) ကို concept level မှာ လေ့လာမယ် — normalization, foreign key design decision
