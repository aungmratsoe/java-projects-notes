# Layered Architecture (အလွှာခွဲ ဗိသုကာပုံစံ) - နက်နက်ရှိုင်းရှိုင်း သင်ယူကြမယ်

## ၁။ ပြဿနာက ဘာလဲ - ဘာလို့ Layer ခွဲရလဲ

Swing application တစ်ခုကို "လွယ်လွယ်" ရေးရင် ဒီလိုဖြစ်တတ်ပါတယ်:

```java
// Button click event ထဲမှာ တန်းရေးထားတာ
saveButton.addActionListener(e -> {
    String sql = "INSERT INTO orders (...) VALUES (...)";
    Connection conn = DriverManager.getConnection(...);
    PreparedStatement ps = conn.prepareStatement(sql);
    // ... SQL logic
    // ... calculation logic
    // ... validation logic
    // အားလုံး GUI event handler ထဲမှာ ရောနေတယ်
});
```

ဒါက **project အသေး (demo, prototype)** အတွက်တော့ အလုပ်ဖြစ်ပါတယ်။ ဒါပေမယ့် project ကြီးလာတာနဲ့အမျှ ပြဿနာတွေ စတင်ပေါ်လာပါတယ်:

- GUI code ထဲမှာ database logic ရော၊ business rule ရော ရောနေရင် **debug လုပ်ရခက်တယ်**
- Database ကို MySQL ကနေ SQLite ပြောင်းချင်ရင် **code နေရာအနှံ့ ရှာပြင်ရမယ်**
- Business logic (ဥပမာ - discount တွက်နည်း) ကို unit test **လုပ်ဖို့ ခက်တယ်** (Swing GUI ကို run မထားရင် test လုပ်လို့မရဘူး)
- Team နဲ့ အလုပ်လုပ်ရင် လူတစ်ယောက်တည်းက file တစ်ခုတည်းကို ပြင်နေရလို့ **conflict ဖြစ်တတ်တယ်**

**Layered Architecture ရဲ့ core idea** ကတော့ - **"concern" (တာဝန်) တစ်ခုချင်းစီကို သီးခြား layer အဖြစ် ခွဲထုတ်ပြီး၊ layer တစ်ခုက နောက် layer တစ်ခုကိုပဲ ခေါ်သုံးခွင့်ပေးတာ** ပါ။ ဒါကို **Separation of Concerns** လို့ခေါ်ပါတယ်။

## ၂။ Layer ၄ ခု (POS system အတွက်)

```
┌─────────────────────────┐
│   View Layer (Swing)    │  ← User မြင်ရတဲ့ GUI
├─────────────────────────┤
│   Service Layer          │  ← Business logic / rules
├─────────────────────────┤
│   DAO Layer               │  ← Database နဲ့ ပြောတဲ့ SQL code
├─────────────────────────┤
│   Model Layer              │  ← Data structure (POJO)
└─────────────────────────┘
           ↓
      Database (MySQL/SQLite)
```

### Model Layer (အခြေခံဆုံး)

Database row တစ်ခုကို Java object အဖြစ် ကိုယ်စားပြုတဲ့ **plain data class** ပါ။ Logic မပါဘူး - data ထားတဲ့ container ပဲ။

> ဥပမာ concept: `Product` object က `productId`, `name`, `price`, `stockQty` field တွေကိုပဲ ကိုင်ထားတယ်။ SQL query မပါဘူး၊ GUI code မပါဘူး။

### DAO Layer (Data Access Object)

**Database နဲ့ ပြောတဲ့ တစ်ခုတည်းသော နေရာ**ပါ။ SQL query တွေ၊ `Connection`, `PreparedStatement`, `ResultSet` handling အားလုံး ဒီမှာပဲ ရှိရမယ်။

> Logic: "Product ID နဲ့ product ရှာချင်ရင် ဘယ် method ကိုခေါ်ရမလဲ" - `getProductById(int id)` လို method သတ်မှတ်ပြီး၊ ဒီ method ထဲမှာပဲ SQL ရှိမယ်။ Layer အပေါ်ကလူတွေ (Service, View) က SQL ဘာမှမသိရဘူး၊ method ခေါ်ရုံပဲ။

**ဒါက ဘာကိုဖြေရှင်းလဲ**: Database ပြောင်းချင်ရင် (MySQL → PostgreSQL) DAO layer ထဲက code ကိုပဲ ပြင်ရမယ်၊ Service/View layer ကို လက်တွေ့ မထိစရာလိုဘူး (SQL syntax ခပ်ကွဲကွဲပေမယ့် interface တူနေရင်)။

### Service Layer (Business Logic)

**Rule/decision logic** အားလုံး ဒီမှာနေရမယ်။ ဥပမာ:

- Order total ဘယ်လိုတွက်မလဲ (tax + discount)
- Stock လုံလောက်ရဲ့လား စစ်တာ
- Permission check (access matrix logic ကို ဒီမှာ enforce လုပ်တာ)

Service layer က DAO layer ကို **ခေါ်သုံး**ပါတယ် (data ရယူဖို့/သိမ်းဖို့)၊ ဒါပေမယ့် SQL ကို တိုက်ရိုက် မရေးဘူး။

> Logic: "Order တစ်ခု place လုပ်ချင်ရင် stock လောက်လား စစ်ရမယ်၊ total ကို တွက်ရမယ်၊ ပြီးမှ DAO ကို ခေါ်ပြီး database ထဲ save ခိုင်းမယ်" - ဒီ decision sequence အားလုံး Service layer ထဲမှာ ရှိတယ်။

### View Layer (Swing GUI)

**User မြင်ရတဲ့ အပိုင်း**ပါ - `JFrame`, `JButton`, `JTable`, event listener တွေ။ ဒီ layer က **Service layer ကိုပဲ ခေါ်ရမယ်**၊ DAO ကို တိုက်ရိုက် ကျော်ခေါ်လို့ မရဘူး၊ SQL ဘာမှ ဒီထဲမှာ လုံးဝ မပါရဘူး။

> Logic: Button ကို click လုပ်လိုက်တာနဲ့ - "ဘယ် data ကို ဘယ် format နဲ့ ပြရမလဲ" ဆိုတာကိုပဲ စဉ်းစားရမယ်၊ "ဘယ်လို calculate လုပ်ရမလဲ" ဆိုတာ View layer ရဲ့ တာဝန် မဟုတ်ဘူး။

## ၃။ **အရေးအကြီးဆုံး Rule**: Direction of Dependency

Layer တွေကြားက ခေါ်ဆိုမှုက **တစ်ဖက်သွား (one-directional)** ဖြစ်ရပါမယ်:

```
View → Service → DAO → Database
```

- View က Service ကို ခေါ်လို့ရတယ်၊ ဒါပေမယ့် Service က View ကို ပြန်ခေါ်လို့ **မရဘူး**
- Service က DAO ကို ခေါ်လို့ရတယ်၊ ဒါပေမယ့် DAO က Service logic ကို သိစရာ **မလိုဘူး**
- View က DAO ကို **ကျော်ပြီး တိုက်ရိုက် ခေါ်လို့ မရဘူး** (Service ကို ဖြတ်ကျော်ခွင့်မရှိ)

**ဘာလို့ ဒီ rule အရေးကြီးလဲ?**

View က DAO ကို ကျော်ခေါ်ခွင့်ပြုလိုက်ရင် - business rule (stock check, permission check) တွေကို GUI code တစ်နေရာမှာ ရေး၊ နောက် GUI screen တစ်ခုမှာ မေ့ကျန်ခဲ့နိုင်ပါတယ် (duplicate logic, inconsistency ဖြစ်တတ်တယ်)။ Service layer ကို **တစ်ခုတည်းသော entry point** အဖြစ် ထားလိုက်ရင် rule အားလုံး တစ်နေရာတည်းမှာပဲ ရှိမယ်၊ GUI ဘယ်နှစ်ခု ထပ်ထည့်ထည့် rule တွေ consistent ဖြစ်နေမယ်။

## ၄။ Concrete Example - "Order တစ်ခု Save လုပ်တာ" ကို Layer အလိုက် ခွဲကြည့်ရအောင်

**View layer** (Cashier က "Save Order" ခလုတ်နှိပ်):

- User ရွေးထားတဲ့ product list + quantity ကို screen ကနေ ဖတ်တယ်
- Service layer ရဲ့ `placeOrder()` method ကို ခေါ်တယ်
- Result ကို success/error dialog ပြတယ်
- (SQL ဘာမှ မပါဘူး၊ calculation ဘာမှ မလုပ်ဘူး)

**Service layer** (`OrderService.placeOrder()`):

- Stock လုံလောက်လား DAO ကို ခေါ်ပြီး စစ်တယ်
- Total price + tax ကို calculate လုပ်တယ်
- User ရဲ့ permission ရှိလား စစ်တယ် (access matrix logic)
- OK ဆိုရင် DAO ကို ခေါ်ပြီး order + order_items ကို save ခိုင်းတယ်
- Stock ကို လျော့ချဖို့ DAO ကို ထပ်ခေါ်တယ်

**DAO layer** (`OrderDAO.insertOrder()`, `ProductDAO.updateStock()`):

- SQL `INSERT INTO orders...`, `UPDATE products SET stock_qty...`
- Transaction (commit/rollback) logic ဒီမှာ ရှိတယ်

**Model layer** (`Order`, `OrderItem`, `Product`):

- Data ကို layer တွေကြား ပို့ဆောင်ဖို့ container class များ

**Logic flow အနှစ်ချုပ်**: View → (calls) → Service → (calls) → DAO → Database. Data က အောက်ကနေ အပေါ်ကို return ပြန်တက်လာတယ် (ResultSet → Model object → Service → View)။

## ၅။ ဒါက Access Matrix Concept နဲ့ ဘယ်လို ဆက်စပ်လဲ

ရှေ့မှာ ပြောခဲ့တဲ့ "GUI + DAO dual-layer enforcement" ဆိုတာ ဒီ layered architecture ပေါ်မှာ တည်ဆောက်ထားတာပါ:

- **View layer**: Permission မရှိရင် button disable (UX အတွက်၊ security အတွက် မဟုတ်)
- **Service layer**: Permission စစ်တဲ့ **အဓိက security checkpoint** - `if (!user.can(...)) throw AccessDeniedException`

Service layer ကို bypass လုပ်ခွင့်မရှိအောင် architecture ကနေတည်ဆောက်ထားရင် - View layer က DAO ကို တိုက်ရိုက်ခေါ်ခွင့် မရှိတဲ့အတွက် security check ကို ကျော်ဖို့ နည်းလမ်း **code architecture အဆင့်ကတည်းက** ပိတ်ဆို့ထားတာပါ။

---

ဒီ concept ကို code structure (folder/package layout: `model/`, `dao/`, `service/`, `view/`) အနေနဲ့ ဘယ်လို project ထဲမှာ organize လုပ်ရမလဲ ဆက်လေ့လာချင်ပါသလား၊ ဒါမှမဟုတ် layer တစ်ခုချင်းစီရဲ့ Java interface/class design (method signature) ကို ပိုနက်နက်ရှိုင်းရှိုင်း ကြည့်ချင်ပါသလား?
