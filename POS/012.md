# Access Matrix (ခွင့်ပြုချက် Matrix) ထည့်သွင်း Database Design

Access Matrix ဆိုတာ **"ဘယ် role (subject) က ဘယ် resource/function (object) ကို ဘာလုပ်ခွင့် (operation) ရှိလဲ"** ဆိုတာကို ဇယားနဲ့ ပြတာပါ။ POS စနစ်တစ်ခုအတွက် အရေးကြီးတဲ့ security concept ဖြစ်ပါတယ်။

## ၁။ Access Matrix သဘောတရား

Access Matrix ရဲ့ mathematical model က -

- **Rows** = Subjects (users/roles)
- **Columns** = Objects (resources/modules)
- **Cell values** = Permissions (Create, Read, Update, Delete)

## ၂။ ကျွန်တော်တို့ POS အတွက် Access Matrix

|Role \ Module|Products/Menu|Orders|Payments|Employees|Reports|Inventory|Discounts|
|---|---|---|---|---|---|---|---|
|**Admin**|CRUD|CRUD|CRUD|CRUD|Read|CRUD|CRUD|
|**Manager**|CRUD|CRUD|Read, Update|Read|Read|CRUD|Create, Read|
|**Cashier**|Read|Create, Read, Update|Create, Read|-|-|Read|Read|
|**Barista**|Read|Read, Update (status)|-|-|-|Read|-|

(C = Create, R = Read, U = Update, D = Delete)

**ရှင်းလင်းချက်:**

- **Admin**: အားလုံးကို ပြောင်းလို့ရ၊ ဝန်ထမ်းစီမံခန့်ခွဲမှုအထိ လုပ်ခွင့်ရှိ
- **Manager**: Discount ခွင့်ပြုနိုင်၊ ဝန်ထမ်း salary/data ကို read ပဲ လုပ်နိုင်၊ delete မလုပ်နိုင်
- **Cashier**: Order ဖန်တီး/ငွေခံနိုင်၊ ဒါပေမယ့် menu ဈေးနှုန်း ပြောင်းလို့မရ
- **Barista**: Order status ကို "preparing → ready" လိုမျိုး update လုပ်ရုံပဲ၊ ကျန်တာအားလုံး read-only

## ၃။ Database ထဲမှာ ဒါကို ဘယ်လို Model လုပ်မလဲ

Access Matrix ကို database မှာ RBAC (Role-Based Access Control) pattern နဲ့ implement လုပ်ပါတယ်:

**roles**

```
role_id (PK)
role_name  -- Admin, Manager, Cashier, Barista
```

**permissions**

```
permission_id (PK)
module_name   -- 'products', 'orders', 'payments', 'employees'...
action        -- 'CREATE', 'READ', 'UPDATE', 'DELETE'
```

**role_permissions** (Access Matrix ရဲ့ core table - Many-to-Many junction)

```
role_id (FK)
permission_id (FK)
PRIMARY KEY (role_id, permission_id)
```

**employees** table မှာ `role_id (FK → roles)` column ထည့်ပါ (ရှေ့က employees table ကို ပြင်ဆင်)

ဒီလိုမျိုး design လုပ်ရင် access matrix ကို **data** အနေနဲ့ database ထဲမှာ ထားလို့ရပြီး၊ code ပြန်ပြင်စရာမလိုဘဲ admin က UI ကနေတောင် role permission တွေကို ပြောင်းလို့ရပါတယ် (hardcode မလုပ်ဘူး)။

## ၄။ Java Swing ထဲမှာ ဘယ်လို Enforce လုပ်မလဲ

Login အောင်မြင်တာနဲ့ employee ရဲ့ role + permissions ကို database ကနေ query ဆွဲပြီး, session object (`LoggedInUser`) ထဲမှာ သိမ်းထားပါ။

```java
public class LoggedInUser {
    private int employeeId;
    private String role;
    private Set<String> permissions; // e.g. "products:UPDATE", "orders:DELETE"

    public boolean can(String module, String action) {
        return permissions.contains(module + ":" + action);
    }
}
```

**GUI level enforcement** - Swing component တွေကို permission အလိုက် ဖျောက်/lock လုပ်ပါ:

```java
if (!currentUser.can("employees", "DELETE")) {
    deleteEmployeeButton.setEnabled(false);
    // (သို့) deleteEmployeeButton.setVisible(false);
}

if (!currentUser.can("products", "UPDATE")) {
    priceField.setEditable(false);
}
```

**Menu-level enforcement** - Cashier login ဆိုရင် "Employee Management" menu item ကို JMenu ထဲက ဖယ်ထုတ်ထားပါ။

## ၅။ အရေးကြီးတဲ့ Security Principle

Swing GUI ထဲမှာ button disable လုပ်တာတင် **မလုံလောက်ဘူး** - ဒါက UX အတွက်ပဲ။ တကယ့် security ကို **DAO layer** မှာချည်း enforce လုပ်ရပါမယ်:

```java
public void deleteEmployee(int employeeId, LoggedInUser actor) throws AccessDeniedException {
    if (!actor.can("employees", "DELETE")) {
        throw new AccessDeniedException("Permission denied");
    }
    // ... SQL DELETE logic
}
```

ဘာလို့လဲဆိုတော့ user တစ်ယောက်က button ကို UI hack (သို့) direct method call နဲ့ ကျော်ခေါ်လို့ရနိုင်လို့ပါ - GUI check ကတစ်ကြိမ်၊ DAO/Service layer check ကတစ်ကြိမ် - **defense in depth** နည်းလမ်းပါ။
